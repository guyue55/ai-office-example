## 二、本轮实际修改（已实施，未提交）

### 2.1 业务码静默降级为 500（P1，已修）

**症状**：两种「符号 + HTTP 状态」组合在出站时找不到码表条目，被 `legacy_code()` 兜底成 `500001 internal_error`，客户端收到 500，而实际是 409 冲突或 422 输入错误。

【实跑】AST 全量扫描 `office-data-service/app`，改前共 49 种 distinct `(symbol, status)` 抛出组合，其中 2 种真缺口：

| 组合 | 改前映射 | 抛出点 |
|---|---|---|
| `identity_claimed@409` | `500001` → HTTP 500 | `office-data-service/app/modules/access/changes.py:37`、`office-data-service/app/modules/access/management.py:374` |
| `invalid_request@422` | `500001` → HTTP 500 | `office-data-service/app/application/account_runner.py:354`、`:361`、`office-data-service/app/application/account_service.py:189`、`office-data-service/app/modules/access/account_operations.py:164`、`office-data-service/app/infrastructure/identity/keycloak.py:96` |

**为什么不是「补一个别名」就能修**：`invalid_request` 的正确业务码是 `400001`，其 `allowed_http_statuses` 只有 `[400]`。若给 `400001` 增加 `@422` 别名，`packages/api-contracts/src/office_contracts/registry.py:118-130` 的 `failure()` 会因 `status not in spec.statuses` 抛 `ConfigurationError("出站错误未登记或状态不符")`——把静默降级换成了运行时崩溃。422 语义对应的码是 `422001 invalid_input`（`allowed_http_statuses: [422]`）。

**实际修法**：按语义改抛错点的 symbol，而非加别名。

| 文件 | 改动 | 理由 |
|---|---|---|
| `office-data-service/app/application/codebook.json` | 给 `409015 identity_claimed` 补 `"legacy_aliases": [{"symbol": "identity_claimed", "status": 409}]`（原为空数组） | 该码已登记且 `availability: current-source`，只是缺别名映射 |
| `office-data-service/app/application/account_runner.py:354-360` | `invalid_request` → `unsupported_operation` | 邮件能力未配置，属「能力未提供」 |
| `office-data-service/app/application/account_runner.py:361` | `invalid_request` → `invalid_input` | 账号未登记邮箱，属输入不满足前提 |
| `office-data-service/app/application/account_service.py:189-194` | `invalid_request` → `invalid_input` | 非 create/reset 操作不能改凭证 |
| `office-data-service/app/modules/access/account_operations.py:164-169` | `invalid_request` → `unsupported_operation` | 同上，邮件能力未配置 |
| `office-data-service/app/infrastructure/identity/keycloak.py:96` | `invalid_request` → `invalid_input` | 身份服务拒绝，属输入资料不符 |

**保留安全网**：`office-data-service/app/entrypoints/errors.py:14` 的 `status = error.status if spec and error.status in spec.statuses else 500` **未放宽**。它把未知组合挡在 500，是正确的兜底；修正后 48 种组合全部合法通过。

**一个必须说清的副作用**：这些抛错点原有的具体中文提示（如「邮件功能尚未配置，请使用临时密码方式」）**不会出现在 JSON 出站响应里**。【实跑】`packages/api-contracts/src/office_contracts/registry.py:128` 是 `Failure(code=code, message=spec.message, meta=meta, **kwargs)`——`message` 恒取码表 `spec.message`，`DomainError.message` 被丢弃。所以修完之后，客户端拿到的是 `422001` + 「请求字段、类型或参数不符合定义」，而不是那句更清楚的提示。

这不是本次改动引入的，是既有设计（统一响应契约要求文案来自码表）。它在 Web 页面侧不影响体验：`office-data-service/app/entrypoints/web/responses.py:101` 的 `web_error_response()` 用的是 `error.message`，页面仍显示具体提示。受影响的是 API／CLI／MCP 消费者。若要保留细粒度提示，需在契约层新增专用错误码，属后续设计议题。

**契约快照是修复的必然产物**：【实跑】运行 `uv run --frozen python scripts/export_contracts.py` 后 `contracts/openapi.json` 新增 59 行，内容全部是在各操作的错误码枚举里 `409011,` 之后插入 `409015,`——因为 `identity_claimed@409` 现在能正确出站，OpenAPI 必须把它列为可能错误码。用 `git stash` 验证过：干净树上 `--check` 通过，漂移确由本次改动引起，非历史遗留。**代码与快照必须一并提交。**

### 2.2 仪表盘账号状态硬编码（P2，已修）

`office-data-service/app/entrypoints/web/templates/dashboard.html:11` 原本无条件输出 `<span class="badge on">账号已启用</span>`，而 `office-data-service/app/modules/access/management.py:51-59` 的 `me()` 早就返回了 `active` 字段。

现改为：

```jinja
{% set active = me.active|default(true) %}
<span class="badge {{ 'on' if active else 'off' }}">{{ '账号已启用' if active else '账号已停用' }}</span>
```

`|default(true)` 不是可有可无的：Jinja 里缺失属性渲染为 falsy，会让所有「mock `me` 但不含 `active`」的合成上下文（`tests/test_web_console.py` 的 fixture、`tests/ui_catalog.py` 的 `me`）误显示「账号已停用」。`.off` 样式已存在于 `office-data-service/app/entrypoints/web/templates/styles.css:272-276`。

**影响范围要如实说**：`active=False` 的员工在现有鉴权下根本到不了这个页面。真实影响是「文案不随状态字段变化」——一旦未来放开停用人员访问，就会失真。这是 P2 一致性问题，不是「停用员工能看到已启用」的信息泄露。

## 四、原始报告中被推翻或收窄的结论

这一节是本轮复核的主要价值：原始报告的若干 P0/P1 定性经不起验证。

### 4.1 「员工改名与启停双表单共端点 = P0 权限旁路」→ 不成立，降为 P2

`office-data-service/app/entrypoints/web/console.py:500-517` 确实只有一个 `POST /console/employees/{identifier}/update`，模板 `employees.html:47-68` 也确实靠隐藏字段传 `active`。

但 `office-data-service/app/modules/access/management.py:302-320` 的 `update_employee()` 有两道检查：先 `if not self.access.allows("access.manage"): self.access.need("employee.update")`，再在 `if obj.active != data.active:` 时二次 `need("access.manage")`。

**结论**：仅持 `employee.update` 的人通过改名表单去停用员工会被 403 拦住，**无法提权**。真实缺陷是「一个 handler 承载两种语义、状态靠隐藏字段传递」的可维护性与误操作面问题，且有服务端兜底。

### 4.2 「Web 每页未设 Cache-Control」→ 不成立

`office-data-service/app/main.py` 对**所有**响应统一设置 `Cache-Control: no-store`，另有 `nosniff`、`no-referrer`、`DENY` 与 CSP。

每页确实会额外解析一次令牌与 `me`（`office-data-service/app/entrypoints/web/console.py:128-131` 的 `render()` 内 `principal_of()` + `application.call(principal, "me", ...)`，部分路由在 `:162` 还会再取一次 principal），但这是性能小问题，不是安全问题。

### 4.3 「10 条 planned 业务码无表达渠道 = P0」→ 不成立

【实跑】`contracts/business-codes.json` 共 63 条，`availability == "planned"` 恰 10 条：`coverage_partial`、`result_stale`、`cursor_invalidated`、`batch_item_not_executed`、`run_not_cancellable`、`result_expired`、`query_complexity_exceeded`、`metric_incompatible`、`required_data_missing`、`rate_limited`。

对这 10 个 key 在 `office-data-service/app` 下逐个 grep → **全部 0 次**。它们是「契约已预留、代码尚未实现」的前瞻码，不是「抛出了但被兜底」。而且 `packages/api-contracts/src/office_contracts/registry.py:185-201` 的 `check_codes()` 明令禁止 planned 码出站，这是有意的设计约束。

### 4.4 「数据域零 Web 页面 = P0 功能缺失」→ 事实成立，定性需改

`office-data-service/app/entrypoints/web/templates/` 下确实没有 project/record/data/export 相关模板。但这是**模板基座的定位选择**：Web 控制台承担管理与助手入口，数据域操作走 CLI/SDK/MCP（见 `AGENTS.md` 与 `office-skills/SKILL.md`）。是否补页属产品决策，不是缺陷。

### 4.5 「每页内联 67KB CSS + 12 个内联 script」→ 数字应为 143KB，且确认无压缩

【实跑】解析 `office-data-service/app/entrypoints/web/templates/base.html` 的 19 个 `{% include %}`，逐个统计被包含文件的字节数：

| 类别 | 内容 | 字节 |
|---|---|---|
| CSS | `styles.css` 31371、`assistant.css` 13041、`shell.css` 9797、`page-patterns.css` 5827、`settings.css` 6103 | 66,139 |
| JS | `assistant-shell.js` 29343、`assistant-view.js` 14072、`assistant-progress.js` 4212、`form-validation.js` 4213、`floating-panels.js` 3723、`assistant-content.js` 3690、`account-role-select.js` 3281、`assistant-transport.js` 2649、`shell.js` 2377、`account-menu.js` 860 | 68,420 |
| HTML 片段 | `_assistant_panel.html` 5764、`_account_menu.html` 1675、`_workspace.html` 1274、`_interactions.html` 563 | 9,276 |
| **合计** | | **143,835** |

所以原始报告的「67KB CSS」只数了 CSS，漏掉了同等体量的 JS。「12 个内联 script」实为 19 个 include。

**并且确认没有传输层压缩**：【实跑】`office-data-service/app/main.py` 无 gzip 中间件（全文无 `GZip`），`deploy/` 下也无 gzip／compress 配置。这意味着每个 HTML 页面响应都携带约 143KB 未压缩的重复内容，且 `Cache-Control: no-store`（`main.py:124`）让浏览器无法复用。

这是真实的传输开销问题，但**不是本轮会改的内容**：引入压缩涉及部署层（网关或 ASGI 中间件）的选择，且需重新验证 CSP 与 SSE 流式响应不受影响。列为 P2 观察项，建议单独立项。相对收益明确：这 143KB 在几乎所有页面上完全相同，压缩后可降至约 30KB，且可配合内容摘要做长缓存。

### 4.6 「助手上下文开关只能键盘操作」→ 表述不准确

`office-data-service/app/entrypoints/web/templates/_assistant_panel.html:16` 的 checkbox 是 `sr-only tabindex="-1" aria-hidden="true"`，但它是**脚本状态载体**，不是用户控件。真实可操作入口是同行的两个按钮（`data-assistant-context-remove` / `data-assistant-context-add`）。原始报告把状态载体误认成了控件。

### 4.7 「时区硬编码 `Asia/Shanghai`」→ 这是显式产品策略，不是缺陷

`office-data-service/app/entrypoints/web/responses.py:27-29` 与 `office-data-service/app/entrypoints/web/tables.py:34` 都硬编码了 `ZoneInfo("Asia/Shanghai")`。但页面文案多处明写「北京时间」：`_filters.html:31`「北京时间，包含结束日」、`audit.html:6`「时间为北京时间」、`client_authorizations.html:18` 列头「时间（北京时间）」。**这是有意的一致实现，不改。**

### 4.8 「`.table-scroll-hint` 无条件输出但桌面隐藏」→ 设计如此

`templates/shell.css:75` 该提示默认 `display:none`，仅在 `@media(max-width:700px)` 内显示，与 `.management-table` 的 `min-width:680px` 配套。桌面不需要提示横向滚动，因为桌面不强制横向滚动。本轮修复的 3 处容器承载的都不是 `.management-table`（`.data-table` 在 ≤700px 走卡片重排），故无需补该提示。

### 5.2 权限码登记来源不唯一（P2）

【实跑】`office-data-service/app/modules/access/catalog.py` 现有 24 个权限码（`DEFINITIONS`）与 36 个审计动作（`AUDIT_ACTIONS`）。对比 17 个迁移中的种子数据，`project.manage`、`record.read.all`、`record.manage.all` 这 3 个码从未出现在任何迁移，自首个提交 `654b315` 起就只存在于 `catalog.py:25`、`:29`、`:31`。

**但「存量实例缺权限」的推论不成立**：`office-data-service/app/modules/access/service.py:219-247` 的 `bootstrap()` 在空员工表时全量灌 `PERMISSIONS`，而所有安装链路（`deploy/install.sh:131`、`deploy/installer/server.py:64-89`）在初始化时都会跑 bootstrap。所以新建实例必然获得这 3 个码。

这是**治理问题**（权限码有两个登记来源、缺一致性校验），不是运行时缺陷。建议补一条校验：`catalog.DEFINITIONS` 的每个码要么在迁移中种过，要么在 bootstrap 中，且两者不得矛盾。

### 5.3 `tests/e2e_*.py` 不被 pytest 收集（P3）

`tests/` 下 9 个脚本（`e2e_account_menu`、`e2e_accounts`、`e2e_client_authorizations`、`e2e_interactions`、`e2e_login_layout`、`e2e_page_review`、`e2e_tables`、`e2e_web_console`、`e2e_workspace`），每个都有 `def main()` 与 `if __name__ == "__main__":`，但没有 `test_` 前缀函数，`pytest --collect-only | grep -c e2e` → **0**。

唯一自动化保障是 `tests/test_browser_probe_imports.py::test_browser_probe_imports_are_valid`：它用 `importlib.util.spec_from_file_location` 逐个 `exec_module` 并断言 `callable(module.main)`。这比「能 import」强一点（会执行模块级代码，例如 `tests/e2e_web_console.py:18` 的 `from live_environment import SERVICE_URL`，后者在 `tests/live_environment.py:5-17` 校验 `OFFICE_TEST_URL` 必须是带端口的本机 HTTP 根地址），但**不执行 `main()`**，所以页面行为、断言的正确性都没有保障。

同文件 `test_browser_page_inventory_is_complete` 确实在跑，且与 `tests/ui-pages.json` 严格比对。本轮复核确认它当前成立：`{% extends %}` 的模板 24 个 == `pages` 24 项，其余 39 个文件 == `components` 39 项，双向差集为空。

**`CONTRIBUTING.md` 全文没有提到 `e2e_*.py`**（`grep -rn 'e2e' CONTRIBUTING.md` 无输出）。这 9 个脚本处于「存在、无文档入口、无 CI、无收集」的不可达状态。其中 `e2e_page_review.py` 承载了页面清单闭合与逐页布局校验这类别处没有的断言，价值不低。

建议要么补进 CONTRIBUTING 的手动验收步骤（它们是唯一需要真实实例 + 真实登录的入口），要么标记为历史遗留并归档。**不建议简单改成 `pytest` 用例**：它们依赖真实 Keycloak 登录与真实实例，塞进 `-m 'not live'` 会造成误报。

### 5.4 审计详情渲染无显式体积上限（P3）

链路：`office-data-service/app/modules/access/service.py:178-190` 的 `audit()` 写 `detail=detail` 无长度约束（`Audit.detail` 是 JSONB），`office-data-service/app/modules/access/outputs.py:92` 的 `detail: dict` 原样外传，`templates/audit.html:25` 用 `<pre class="code">{{ item.detail }}</pre>` 全量渲染。

**但实际体积受控**：全量检查所有 `access.audit(` 调用点，detail 均为 2–6 个小键的扁平 dict；唯一较大的是 `session.change` 的 `reason`（`office-data-service/app/modules/access/session_schemas.py:40` 限定 `max_length=200`）与 `clients` 列表。且 `.code` 样式有 `overflow-wrap: anywhere`，不会撑破布局。

属理论风险。若未来新增 detail 较大的审计动作，应在写入侧或渲染侧加体积上限。
