# 员工开通与身份绑定设计复核

## 当前决定：简化日常开通并保证首次角色（2026-11-05）

本节替代下文历史方案中“默认角色可取消”“外部身份接入页”“未开通访问记录页及人员页提示”的设计。下文保留作为审查和失败证据，不代表当前界面。

- 普通 Web 只保留「新建员工」和「关联已有账号」。移除手动绑定、待认领页面及其五条 GET／POST 路由，旧地址返回404；人员页也不再读取待认领记录。既有身份绑定、访问记录和后端 API／MCP／SDK 运维能力保留，不清理数据。
- 两条常规表单固定说明首次关联内置普通员工角色，不提供“不授予角色”开关。预览仍显示实际角色及当前权限，确认摘要、版本、幂等和账号后续步骤不变。
- 账号创建／关联命令省略或传 null 的 role_ids 解析为 builtin_key=employee 的内置角色；显式非空角色列表保留原选择，不额外叠加普通员工权限；空列表在输入模型和领域校验均拒绝422。保证的是首次关联至少一个角色，不强制所有自定义角色都继承员工权限。
- 后端外部绑定／认领仍供特殊接入运维使用，assign_default_role 仅接受 true；旧客户端传 false 返回422，不能静默忽略。该能力不是普通员工开户后的第二步。
- 默认角色缺失返回409，不退化为无角色开通。角色权限仍可由有权管理员配置；“关联普通员工角色”不等于永久保证固定权限集合。后续撤权、停用、重新启用、登录与重启均不补权；既有无角色人员也不自动回填。
- 不新增迁移，不改变登录准入或托管边界。未配置账号管理连接时常规开户不可用，外部身份须走既有运维接口；本轮未更新在用实例。

### 本次联网研究与二次复核

[Keycloak 默认角色](https://www.keycloak.org/docs/latest/server_admin/index.html)用于用户创建或身份代理导入时分配角色映射，不能据此推导本项目每次登录都应补权。[Microsoft Entra 用户预配](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/user-provisioning)明确区分 SSO 与应用用户预配。[OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)要求最小权限和默认拒绝；其[官方源码](https://github.com/OWASP/CheatSheetSeries/blob/master/cheatsheets/Authorization_Cheat_Sheet.md)用于正文复核。三者支持生命周期分离与服务端校验；“取消零角色开通选择”是本项目产品决定，不宣称规范统一要求。

代码复核覆盖输入模型、领域角色解析、预览摘要、执行器重新核验、身份准入及管理撤权。隔离数据库新增反例：默认角色缺失、显式自定义角色不叠加默认权限、预览后角色变化、撤权后启停与新登录。测试首轮错误地直接修改受管人员启停，被现有409保护拒绝；改走账号启停后，旧合成令牌又正确收到401，随后改为验证旧令牌拒绝及新合成令牌无角色。两次失败均属测试路径修正，未放宽产品保护。

当前验收结果和未验边界见工作台重构账本本轮条目。

## 结论

当前实现不是“登录即自动分配普通员工角色”，而是“管理员开通时默认分配，可取消”。新建员工成功后已经建立账号绑定及所选角色，无需再次绑定或认领。常规界面应优先保留“新建员工”和“关联已有账号”；手填登录标识不适合作为同级日常入口，待认领则应定位为未开通访问的异常处理。下述入口收敛、确认和分页已在源码实施，现有运行实例尚未更新。

## 代码证据与二次复核

| 问题 | 真实实现 | 复核位置 |
|---|---|---|
| 登录是否自动开通 | 根据 issuer／subject 查已有人员；缺失、停用或安全冻结返回403，不创建人员或授予角色 | `modules/access/service.py` 的 `Access.create`；`application/service.py` 在拒绝后登记未知身份 |
| 默认角色何时授予 | 手动绑定、认领调用 `assign_role`；账号新建／关联在预览中解析角色并在执行中写入 | `modules/access/provisioning.py`、`management.py`、`account_operations.py`、`application/account_runner.py` |
| 新建员工是否已绑定 | 执行写入 Employee、IdentityLink 和 EmployeeRole；开户还包含凭证与启用等后续阶段，不能把预览或部分成功称为完成 | `application/account_runner.py` |
| 已开通员工还会待认领吗 | 队列排除已有 IdentityLink；留痕也跳过已有绑定，包括已停用员工 | `management.py` 的 `pending_identities`；`service.py` 的 `trace_pending_identity` |
| 三条绑定路径是否等价 | 搜索关联产生 `managed=True` 绑定；手动与认领不设置该标志，按模型默认属于非受管绑定 | `application/account_runner.py`、`management.py`、`infrastructure/models.py` |
| 是否能直接移除旧入口 | 账号管理是可选配置；未配置时搜索／开户不可用，但受信身份登录和管理员绑定仍可使用 | `application/account_service.py`、`entrypoints/web/console.py` |
| 队列数量是否完整 | 审查时仅最早50条；本次已补筛选总数、分页和稳定排序，人员页只取1条及总数提示 | `management.py` 的 `pending_identities` |

上述源码路径均相对 `office-data-service/app/`。只看页面文案容易把“首次开通默认授予”误读为“首次登录默认授予”；本轮分别检查了验证、拒绝留痕、预览、执行和列表过滤链路。

## 官方资料与适用边界

1. [OpenID Connect Core 1.0，5.7 Claim Stability and Uniqueness](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)：稳定身份依据为 issuer 和 subject 的组合，不应以姓名、邮箱或用户名自动合并员工。此规范支持身份关联键选择，不要求用户手填该键。
2. [Keycloak Server Administration，First Login Flow](https://www.keycloak.org/docs/latest/server_admin/index.html#_identity_broker_first_login)：支持多种首次登录策略；自动关联账号需考虑注册来源、身份资料与信任范围。文档警告在允许任意用户名／邮箱注册的环境中使用 AutoLink 的危险。此处讨论外部身份提供方与 Keycloak 的关联，是安全设计参考，不是本项目业务人员开通的直接实现。
3. [Microsoft Entra，What is automated app user provisioning?](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/user-provisioning)：区分单点登录与应用人员预配，并讨论手工、自动预配、JIT及SCIM。可据此选择明确的入职和离职流程，不能据“支持SSO”推导“应对所有登录者授予业务权限”。本项目本轮未增加JIT或SCIM。

资料通过联网读取官方正文核对。企业是否允许所有统一身份账号进入本应用，属于产品与组织准入策略；上述资料不能替用户决定。

## 设计依据与处理结果

- 日常路径：新建员工完成开户与基础授权；已有账号通过搜索核对后关联。角色可另行调整，不为已完成员工再要求一次认领。
- 手动绑定：已移至独立「外部身份接入」页，人员页底部保留低强调入口，说明仅适用于外部维护账号或未配置管理连接的情形。页面不能单凭已配置连接推断所有账号都应接管，因此保留管理员显式选择；非受管绑定仍可用。
- 待认领：已改为「未开通访问记录」独立页，人员页仅有记录时提示总数；集中搜索和分页，不将未知身份描述为正式员工或授权申请。
- 两条外部开通路径均先预览再确认，复用既有 access.change.preview/apply。展示姓名、真实 issuer／subject、实际角色名称和当前权限；开通不接管凭证，取消不写入。认领预览摘要新增绑定实际身份，执行时重新核对，不信任客户端隐藏字段。
- 已同步服务端、HTTP、MCP、SDK、CLI与Agent目录的 page／limit／q，保留默认50条；搜索按字面匹配，排序采用首次访问时间和唯一ID。总数为当前筛选下的导航参考，不是跨请求冻结快照；沿用共享分页的10万偏移预算，不宣称无上限浏览。
- 若采用“所有合资格员工首次登录自动开通”，需单独定义可信员工范围、触发条件、一次性授予、撤权不补回及停用不重建；不能只删除认领UI或把默认角色授予放进每次登录。

## 首次审查验证（实施前）

本轮运行 `tests/test_review_regressions.py` 和 `tests/test_web_console.py` 中 pending／binding_forwards 相关离线用例：8通过、62未选中。覆盖拒绝后留痕、留痕失败不改原拒绝、已绑定身份跳过、页面转义／日期及绑定表单显式角色选择。

## 实施复核与限制（2026-11-05）

- 隔离PostgreSQL用例通过：63条记录跨页读取、相同时间稳定排序、字面百分号搜索、超出末页，以及其他来源／已处理／已有绑定（含停用）排除；预览零写入、摘要不符409、重复开通拒绝、普通员工403、默认角色开关、两条路径均为非受管绑定。
- 独立真实Web路由浏览器用例通过：表格主要操作保留文字，弹窗进入预览，取消零执行；手动接入预览后确认恰好一次执行。此用例使用合成身份和执行适配，与上述真实数据库用例分别证明界面及事务边界，不等于真实身份服务开户成功。
- 二次复核发现：共享弹窗的普通POST要求写入回执，预览表单必须标记 data-native-submit；表格增强默认将操作替换为图标，单一主要流程使用 data-keep-label 保留可发现文字。浏览器测试起初选错共享弹窗，已改为按实际对话框名称定位；不能把测试定位错误说成用户界面缺陷。
- 首轮完整离线759通过、1失败；失败为新测试误要求数值上限在Web层拒绝，实际上应用层已正确返回422，按分层校验修正断言。首轮共享浏览器35通过、2失败，来自迁移入口后的旧选择器／旧队列断言，修正后两项定向复验通过。最终门禁结果记录于工作台重构账本。
- 已将新增浏览器和隔离PG用例纳入CI命令及页面目录；工作流修改未在远端运行。本轮没有连接真实人员账号、读取登录凭证、执行在用数据库写入或更新运行实例；真实账号管理与身份提供方链路未重验。无自动开通、JIT或SCIM策略变更。
